# 配置驱动的用例编排框架 —— 设计文档

> 基于《Spring Boot 六边形架构包结构设计指南》的改造方案：将「应用服务编排用例 + Controller 绑定端点」的固定样板，下沉为 **框架能力**——usecase 由配置声明、step 自动装配、RouterFunction 完成 endpoint 绑定。
>
> 技术栈基线（沿用原 solution）：Java 21 · Spring Boot 4.1.x · Spring Framework 7 · Maven 3.9+。

---

## 一、改造动机

原 solution 中每新增一个用例，要按模板写一串类型：

```text
GetUserUseCase（入端口接口）→ UserService（编排实现）→ UserController（端点绑定）
→ UserDto / UserResponse / UserWebMapper / @ExceptionHandler 映射 ……
```

对于「**加载 → 调外部服务 → 转换 → 保存**」这类结构化用例，这些代码高度同构。观察它们的共性：

| 样板成分 | 共性抽象 |
|---------|---------|
| `repository.findById(...)` | **DataLoader**：从出端口取数据 |
| `paymentGateway.charge(...)` / RestClient 调用 | **HttpRequester**：调外部 HTTP（常需认证） |
| `UserDto.from(user)` / 对象映射 | **DataTransformer**：数据转换 |
| `repository.save(...)` | **DataSaver**：写回出端口 |
| `@GetMapping("/users/{id}")` + 调 Service | **endpoint ↔ usecase 绑定** |
| `GlobalExceptionHandler` | 异常 → 传输层响应映射 |

改造思路：**把这些同构成分抽象为 step 角色，用例变成 step 的有序管道，管道由配置声明、框架装配，端点用 RouterFunction 动态绑定。**

适用边界（重要）：框架面向**结构化、可声明的编排型用例**；复杂状态机、长事务编排、强领域计算的用例仍应沿用原 solution 的手写 `application.service` 方式，两者共存（框架的自定义 `ref` step 也提供了逃生舱）。

## 二、总体架构

```text
                        ┌─────────────────────────── 启动期（装配）───────────────────────────┐
                        │                                                                     │
 application.yml ──→ UseCaseProperties ──→ UseCaseAssembler ──→ UseCaseRegistry               │
 (usecase.definitions)   (@ConfigurationProperties)   │            (id → UseCase)             │
                                                     │ 按 step 定义解析：                     │
                        ┌────────────────────────────┤                                       │
                        ▼                            ▼                                       │
              StepFactory 注册表              BeanFactory.getBean(ref)                        │
              (type → 工厂)                   (自定义 Step Bean)                              │
                        │                                                                     │
                        └────────────→ UseCase = UseCase.EndpointSpec + List<Step>            │
                                                                                              │
                        RouterFunction 绑定：每个 UseCase → route(method+path → 管道执行)       │
                        └─────────────────────────────────────────────────────────────────────┘

                        ┌─────────────────────────── 运行期（调用）───────────────────────────┐
 HTTP 请求 ──→ RouterFunction ──→ StepContext（直接持有 ServerRequest）                      │
                        │                                         │  for step in steps:      │
                        │                                         ▼                          │
                        │                    DataLoader → DataTransformer → HttpRequester → DataSaver
                        │                    （payload 主流转，#vars 旁路流转）               │
                        │                                         │                          │
                        └────────── ApiResponse.success(payload) ◄┘                          │
                                     onError → 统一异常映射（404/502/500 + 错误码）            │
```

> **多模块布局（已落地）**：工程已拆为 Maven 多模块——`framework-core`（框架本体库 jar，含 `AutoConfiguration.imports`，经 Spring Boot 自动配置装配，可单独发布为内部 starter）与 `demo`（演示应用，依赖 core）。上文包结构中 `framework` 子树即 `framework-core` 模块，其余为 `demo` 模块；包名保持 `com.example.myapp.*` 前缀不变（demo 的组件扫描天然覆盖，core 作为独立 jar 发布时可整体重命名包前缀）。

**与原 solution 的对应关系**：

| 原 solution | 改造后 | 说明 |
|------------|-------|------|
| `port.in` UseCase 接口 + `service` 实现 | YAML `usecase.definitions` + 管道 | 结构化用例改为声明式；复杂用例仍可手写 service |
| `@RestController` | `RouterFunction`（配置生成） | 函数式端点；与注解式 Controller 可共存 |
| `GlobalExceptionHandler` | router `onError` 统一映射 | 自包含于路由，规则见第五章 |
| Web/应用 DTO + Mapper | `dataTransformer` step（SpEL 或 ref Bean） | 简单映射用 SpEL，复杂映射用 Java Bean |
| 出端口 / 适配器 | **不变** | step 的 SpEL 表达式直接引用出端口 Bean |

**六边形铁律的保持**：依赖方向依然向内——step 表达式引用的是 `application.port.out` 的接口 Bean，不感知 JPA/HTTP 细节；领域层依然零依赖（`DomainException implements ErrorCoded` 是务实妥协，去掉后框架反射回退，见 5.2）。

## 三、核心抽象（framework.core）

### 3.1 Step 与四个核心角色接口

```java
@FunctionalInterface
public interface Step {
    void execute(StepContext context);
    default String name() { return getClass().getSimpleName(); }
}

public interface DataLoader extends Step {}      // 出端口读数据 → payload
public interface DataTransformer extends Step {} // payload → payload
public interface HttpRequester extends Step {}   // 调外部 HTTP（可挂 AuthHandler）
public interface DataSaver extends Step {}       // payload → 出端口
```

角色接口只覆盖**主数据流**的四个核心抽象（加载 → 转换 → 调用 → 保存），同时作为治理锚点——配置审查、
步骤耗时统计、权限管控可按角色维度做。其余内置 step 类型按语义就近归并，不再单设角色接口：

| 内置类型 | 归并 | 理由 |
|---------|------|------|
| `encoder` / `decoder` | 实现 `DataTransformer` | 编解码是数据变换的特例 |
| `starter` / `logging` / `validator` / `usecase` / `eventPublisher` | 直接实现 `Step` | 守卫 / 横切 / 组合动作，不产主数据 |

自定义 Step 同理：命中主数据流语义时实现对应角色接口，否则实现 `Step` 即可。未来出现稳定的治理
维度时（如按事件发布角色统计），再按需增设角色接口。

### 3.2 StepContext：三通道数据流

```
payload ── 主数据通道：逐段被 加载→转换→保存，最终以 ApiResponse.data 返回
vars    ── 旁路通道：step 配 as: xxx 时写入 #vars.xxx，供后续步骤引用
biz     ── 关键数据区：starter 在用例开始写入 businessId/租户/渠道等；Web 入口自动种子化 traceId
          （X-Request-Id 经白名单 [A-Za-z0-9_-]{8,128} 校验，不合法即重新生成，防日志注入）；
          非 null 值同步日志 MDC（biz.* 前缀，值剥离控制字符；traceId 亦写入 MDC），请求结束自动清理
request ── 入站请求抽象（#path / #query / #headers / #body）
```

`as` 语义（统一定义）：**配置 `as` → 结果写入 `#vars[as]` 且 payload 不变**；未配置 → 结果写入 payload（dataSaver 例外：表达式返回 null 时保留原 payload，防止 void save 清空数据）。

`StepContext` 直接持有 Spring 的 `ServerRequest`——core 模块直接依赖 spring-webmvc（`RouterFunction`、`HttpMethod` 等本就在核心模型与 web 包中使用），不再维持传输层桥接（原 `ExchangeRequest` 抽象 / `WebExchangeRequest` 适配器已移除，2026-08-19 决策）。请求体惰性解析（JSON → Map/List、语法错误映射 400、非 JSON 按纯文本）由 `StepContext#getBody` 承担；管道外编程调用用 `StepContext.standalone()`（无入站请求，各请求视图为空 Map / null）；单元测试用 Mockito mock `ServerRequest`（测试源集 `TestServerRequests` 工厂）构造富请求，保持零容器。

### 3.3 UseCase：端点 + 有序管道（区分 endpoint 用例与 shared 用例）

```java
public final class UseCase {
    // id / description / UseCase.EndpointSpec(method, path, status) / List<Step> / shared
    public Object execute(StepContext context) {
        for (Step step : steps) {
            try { step.execute(context); }
            catch (StepExecutionException e) { throw e; }
            catch (RuntimeException e) { throw new StepExecutionException(id, step.name(), e); }
        }
        return context.getPayload();
    }
}
```

异常包装携带 `useCaseId + stepName`，传输层沿 cause 链还原原始异常做映射。

用例分两级：**endpoint 用例**绑定路由对外服务；**shared 用例**（`shared: true`，端点为 null）不参与路由，只能被 `type: usecase` 的 step 作为子用例嵌入。子用例内抛出的 `StepExecutionException` 原样上抛，父用例不再二次包装——错误链始终指向最内层失败步骤。

## 四、配置 Schema 与自动装配

### 4.1 完整配置示例（可直接运行的 demo）

```yaml
usecase:
  error-mappings:
    com.example.myapp.domain.exception.UserNotFoundException: 404
  definitions:
    # shared 用例：不绑定 endpoint，仅作为子用例被嵌入
    - id: userBaseEnrichment
      shared: true
      steps:
        - { name: loadUser, type: dataLoader,      config: { expression: "@userRepository.getById(T(com.example.myapp.domain.model.UserId).of(#payload))" } }
        - { name: toDto,    type: dataTransformer, config: { expression: "T(com.example.myapp.application.dto.UserDto).from(#payload)" } }

    - id: getUser
      endpoint: { method: GET, path: /api/v1/users/{id} }     # status 缺省 200
      steps:
        - name: start                                         # starter：提取 businessId 入 biz 关键数据区
          type: starter
          config:
            keys:
              businessId: "#path.id"
        - name: validateInput                                 # validator 函数模式：表达式 false 即失败
          type: validator
          config:
            expression: "#biz.businessId != null and !#biz.businessId.isBlank()"
            message: "businessId 不能为空"
            errorCode: "INVALID_INPUT"
        - name: loadUserBase                                  # 子用例调用：ref = 目标用例 id
          type: usecase
          ref: userBaseEnrichment
          config: { input: "#biz.businessId" }                # 未配 as → 子结果串联为父 payload

    - id: getUserProfile
      endpoint: { method: GET, path: /api/v1/users/{id}/profile }
      steps:
        - { name: start, type: starter, config: { keys: { businessId: "#path.id", channel: "#{headers['X-Channel']}" } } }
        - { name: loadUserBase, type: usecase, ref: userBaseEnrichment, config: { input: "#biz.businessId" } }
        - name: fetchCredit
          type: httpRequester
          config:
            method: GET                                        # 缺省 GET
            url: "${credit.base-url}/stub/credit/scores/{userId}"   # ${} 走 Spring 占位符
            uriVariables: { userId: "#biz.businessId" }        # URI 模板变量，值支持表达式
            headers: { X-Request-From: "usecase-framework" }   # 值：字面量/#{...}模板/SpEL
            auth:
              scheme: bearer                                   # 装配期校验 scheme 存在
              options: { token: "demo-credit-token" }
            as: credit                                         # 旁路输出
        - { name: checkCreditPass, type: validator, config: { expression: "#vars.credit.score >= 600", message: "用户 #{biz.businessId} 信用分不足（>=600 方可生成画像）", errorCode: "CREDIT_TOO_LOW" } }
        - { name: logCredit, type: logging, config: { level: INFO, message: "用户 #{biz.businessId} 信用分: #{vars.credit.score}" } }
        - { name: encodeUserId, type: encoder, config: { algorithm: base64url, source: "#biz.businessId", as: encodedUserId } }
        - { name: mergeProfile, ref: userProfileTransformer }  # 自定义 Bean，与 type 二选一
        - { name: saveSnapshot, type: dataSaver, config: { expression: "@profileSnapshotRepository.save(#payload)" } }

    - id: getUserByToken                                     # 演示 decoder：base64url token 还原 userId
      endpoint: { method: GET, path: /api/v1/users/token/{token} }
      steps:
        - { name: start,       type: starter, config: { keys: { token: "#path.token" } } }
        - { name: decodeToken, type: decoder, config: { algorithm: base64url, source: "#path.token" } }   # 结果写回 payload
        - { name: loadUserBase, type: usecase, ref: userBaseEnrichment }   # input 缺省 #payload

    - id: createUserSnapshot                                 # 演示 schema 校验 + isolate 子用例
      endpoint: { method: POST, path: /api/v1/user-snapshots }
      steps:
        - { name: start, type: starter, config: { keys: { businessId: "#body.userId" } } }
        - name: validateBody                                 # validator schema 模式（装配期预编译）
          type: validator
          config:
            target: "#body"                                  # 校验请求体（缺省 #payload）
            schema:
              type: object
              required: [userId, name]
              properties:
                userId: { type: string, minLength: 1 }
                name:   { type: string, minLength: 1 }
                tags:   { type: array, items: { type: string } }
              additionalProperties: false
        - name: checkUserExists                              # isolate 旁路：确认用户存在，不污染父上下文
          type: usecase
          ref: userBaseEnrichment
          config: { input: "#body.userId", as: userDto, isolate: true }
        - { name: logCreation, type: logging, config: { message: "为用户 #{vars.userDto.name}(#{vars.userDto.id}) 创建快照" } }
        - { name: toSnapshot,  type: dataTransformer, config: { expression: "{userId: #body.userId, name: #body.name, tags: #body.tags, ownerName: #vars.userDto.name}" } }
        - { name: saveSnapshot, type: dataSaver, config: { expression: "@profileSnapshotRepository.save(#payload)" } }
```

### 4.2 SpEL 求值上下文

| 变量 | 含义 | 示例 |
|------|------|------|
| `#path` / `#query` / `#headers` | 路径变量 / 查询参数 / 请求头（Map） | `#path.id` |
| `#body` | 请求体（JSON → Map/List，惰性读取） | `#body.items[0].quantity` |
| `#payload` | 当前主数据 | `#payload.id` |
| `#vars` | 旁路命名结果 | `#vars.credit.score` |
| `#biz` | 关键数据区（starter 写入） | `#biz.businessId` |
| `@beanName` | 容器任意 Bean（出端口、领域服务…） | `@userRepository.getById(...)` |
| `T(fqcn)` | 类型引用 | `T(com.example.UserId).of(...)` |

内嵌值（header / uriVariable）智能解析三规则：含 `#{` → 模板拼接（以 StepContext 为根对象，如 `"Bearer #{vars.token}"`、`"#{path.id}"`）；以 `#`/`@`/`T(` 开头 → 完整 SpEL；其余 → 字面量。

### 4.3 装配流程（三遍，启动期 fail-fast）

```
UseCaseAssembler.assemble(definitions)
  ├─ 第一遍 定义校验：id 非空且唯一；非 shared 用例 endpoint.method/path 必填且 method 合法；
  │    steps 非空（shared 用例豁免端点校验）；
  │    starter 的 keys 不得写保留 biz 键 traceId（装配即报错）；shared 用例内含 starter 打 WARN
  ├─ 第二遍 子用例引用图：type=usecase 的 step 其 ref 必填且必须指向已定义用例 id；
  │    DFS 检测循环引用（含自引用），命中即报完整链路（如 [a, b, a]）
  └─ 第三遍 逐 step 构建：
       ref 与 type 必须二选一（唯一特例：type=usecase 时 ref 承载目标用例 id，允许共存）
       ref  → beanFactory.getBean(ref, Step.class)          # 不存在即报错
       type → StepFactory 表查找（未知类型列出可用类型）→ create(def)
               ├─ httpRequester 工厂在装配期校验 auth scheme 并调 AuthHandler.validate(options)
               ├─ eventPublisher 工厂在装配期校验发布器（不实例化）：Bean 存在且类型匹配 /
               │    缺省时唯一实现（多候选须有 @Primary），运行期首次发布才解析
               ├─ decoder 工厂在装配期校验算法可逆
               ├─ validator 工厂在装配期强制 expression/schema 二选一，并预编译 JSON Schema
               └─ usecase 工厂注入 Supplier<UseCaseRegistry>（延迟解析，规避装配期循环依赖）
  → UseCaseRegistry（LinkedHashMap，保序）
```

任何配置错误在启动期抛 `UseCaseAssemblyException`，不进入运行期——配置即契约。

## 五、内置 step 详解

### 5.1 SpEL 三件套（dataLoader / dataTransformer / dataSaver）

配置：`expression`（必填）、`as`（可选）、`onNull`（可选，仅 dataTransformer 生效）。三者共享「结果落地规则」，仅 null 处理不同（saver 恒不覆盖）。

- `onNull: keep`（dataTransformer）：表达式为 null 时保留原 payload；缺省 OVERWRITE——null 清空 payload 并打 WARN（配置写错字段名是最常见的 null 成因）。

内置 step 的 SpEL **求值失败**（非 JSON 体上取 `#body.xxx`、null 导航等）统一收口为 400（`StepValidationException`，消息附 step 名与求值错误，经 `StepExpressionEvaluator.evaluate/resolve(expr, ctx, stepName)` 收口）；Bean 方法抛出的领域异常不经 SpEL 包装、原样传播走领域映射。

典型写法：

```yaml
# dataLoader：调用出端口
expression: "@userRepository.getById(T(com.example.UserId).of(#path.id))"
# dataTransformer：静态工厂映射
expression: "T(com.example.UserDto).from(#payload)"
# dataSaver：写回出端口，返回值（带主键实体）成为新 payload
expression: "@orderRepository.save(#payload)"
```

> **表达式缓存**：`StepExpressionEvaluator` 按原文缓存解析结果（`Expression` 不可变、线程安全），键空间仅来自 YAML 配置（有限集合），避免每请求每 step 重复构建 SpEL 语法树。

### 5.2 httpRequester

| 配置项 | 必填 | 说明 |
|-------|-----|------|
| `method` | 否（GET） | GET/POST/PUT/DELETE/PATCH |
| `url` | 是 | 支持 `${}` 占位符 + `{var}` URI 模板 |
| `uriVariables` | 否 | 模板变量，值支持表达式 |
| `headers` | 否 | 值：字面量 / `#{...}` / SpEL |
| `body` | 否 | SpEL 表达式，结果由消息转换器序列化（对象→JSON） |
| `auth` | 否 | `scheme` + `options`，见 5.3 |
| `as` | 否 | 旁路输出到 `#vars` |

错误语义：非 2xx → `HttpStepException`（带下游状态码与响应摘要）；连接失败/超时 → `ResourceAccessException`；两者统一映射 **502 DOWNSTREAM_ERROR**（不回显下游报文）。

### 5.3 starter（关键数据区装载）

```yaml
- name: start
  type: starter
  config:
    keys:
      businessId: "#path.id"                    # 约定键：关键业务 ID
      tenantId: "#headers['X-Tenant-Id']"       # 完整 SpEL
      channel: "#{headers['X-Channel']}"        # 模板形式
      source: "app"                             # 字面量
```

- 每个键按「字面量 / #{...} 模板 / SpEL」三规则解析，写入 `biz` 关键数据区；后续步骤经 `#biz.xxx` 引用；
- 非 null 值同步到日志 MDC（键名 `biz.<key>`），请求结束由 Web 层统一清理（防线程复用串号）；
- 推荐放在管道首位；`businessId` 为约定关键键名，logging / 排障围绕它展开。

### 5.4 logging（管道日志）

| 配置项 | 必填 | 说明 |
|-------|-----|------|
| `level` | 否（INFO） | TRACE/DEBUG/INFO/WARN/ERROR（SLF4J Level），非法值装配期报错 |
| `message` | 否 | `#{...}` 模板（可引用 biz/vars/payload），缺省打印 payload |

日志 category 为 `usecase.<useCaseId>.step.<stepName>`，可按用例或步骤名定向治理级别。logging 步骤不产生/修改任何数据。

### 5.5 encoder / decoder（编解码）

| 配置项 | 必填 | 说明 |
|-------|-----|------|
| `algorithm` | 是 | base64 / base64url / url / hex / md5 / sha256（自定义 `Codec` Bean 可扩展） |
| `source` | 否（#payload） | 输入 SpEL 表达式 |
| `as` | 否 | 旁路输出；缺省写回 payload |

`md5`/`sha256` 为单向摘要：decoder 引用时在**启动装配期**即报错（fail-fast），不会拖延到运行期。

### 5.6 validator（入口校验）

一般放在管道入口（紧随 starter），把非法输入挡在管道之外。两种**互斥**模式（装配期强制二选一）：

| 配置项 | 必填 | 说明 |
|-------|-----|------|
| `expression` | 二选一 | 函数式校验：SpEL 返回 `false` 即失败；SpEL **求值失败**（如 null 导航）同样映射 400（消息附求值错误）；表达式调用的 Bean 方法抛出的领域异常不经 SpEL 包装，**原样传播**走领域映射 |
| `schema` | 二选一 | JSON Schema（2020-12 方言，networknt 3.x），**装配期预编译**为 `Schema`，运行期零解析开销 |
| `target` | 否（#payload） | 校验目标表达式，入口校验常用 `#body` |
| `message` | 否 | 失败消息，支持 `#{}` 模板 |
| `errorCode` | 否（VALIDATION_ERROR） | 稳定错误码，随 `ApiResponse.code` 返回 |

失败抛 `StepValidationException`（实现 `ErrorCoded`，`defaultHttpStatus() = 400`）：schema 模式收集全部字段错误明细（最多 5 条拼接），如 `must be at least 1 characters long; required property 'userId' not found`。

**选型说明**：networknt json-schema-validator 从 3.0.x 起迁移至 Jackson 3（`tools.jackson`），与 Spring Boot 4 的 Jackson 基线一致；其 3.x 为重写版 API（`SchemaRegistry.withDefaultDialect(DRAFT_2020_12).getSchema(node)` → `schema.validate(node)` 返回 `List<Error>`），注意与 1.x 的 `JsonSchemaFactory` 系 API 不兼容。

### 5.7 usecase（子用例调用）

把一个 shared 用例嵌入当前管道，实现**用例级复用**（公共加载、公共 enrichment、准入检查等）：

| 配置项 | 必填 | 说明 |
|-------|-----|------|
| `ref`（step 级） | 是 | 目标用例 id（`type: usecase` 是唯一允许 ref+type 共存的特例：ref 承载用例 id 而非 Bean 名） |
| `input` | 否（#payload） | 子用例初始 payload 表达式 |
| `as` | 否 | 旁路：结果写 `#vars[as]` 且父 payload 恢复；缺省串联：子结果成为父 payload |
| `isolate` | 否（false） | `true` 时子在全新 vars 中执行（不污染父），biz **拷贝继承**（子可读父的 businessId，子的修改不回传），**MDC 快照恢复**（子内 MDC 写入返回时回滚，不污染父管道日志） |

数据传递语义汇总：

```
串联（默认）:  ctx.payload = eval(input); target.execute(ctx);            // 子结果即父 payload，vars/biz 共享
旁路（as）:    同上执行后 vars[as] = 子结果，恢复父 payload                 // 适合"确认存在性"等纯检查
隔离 isolate:  全新子 ctx（biz 拷贝、vars 全新）执行，结果按 as 规则落到父    // 强隔离，绝不污染父上下文
               （MDC 是线程级单例而非 Map 拷贝：子内 MDC 写入经快照/恢复在返回时回滚）
```

`UseCaseRegistry` 经 `Supplier` 延迟注入 step（step 创建于装配期，registry 此时尚未就绪）；引用的存在性与循环引用已由装配器第二遍统一校验，运行期 `require()` 必然命中。

### 5.8 Java 代码调用子用例（UseCaseInvoker / AbstractUseCaseClient）

shared 用例除 YAML 嵌入外，还需支持编程式调用（自定义 Step Bean、领域服务、调度任务）。框架提供两层 API：

```
StepContextHolder（core，ThreadLocal）
  └─ UseCase.execute 执行期绑定当前上下文；嵌套保存/恢复；结束必然清理
UseCaseInvoker（core，自动注册 Bean）
  ├─ invoke(id, input)            管道内共享上下文（vars/biz 互通、父 payload 自动恢复）；管道外退化为独立调用
  ├─ invokeIsolated(id, input)    隔离：vars 全新、biz 拷贝继承、MDC 快照恢复
  └─ invokeStandalone(id, input)  独立：全新上下文 + 空请求抽象，自动种子化 traceId（MDC 快照恢复）
AbstractUseCaseClient<I, O>（core，基类）
  └─ 业务方继承：绑定用例 id + 结果类型，获得类型安全的 invoke/invokeIsolated/invokeStandalone
```

```java
@Component
public class UserBaseClient extends AbstractUseCaseClient<String, UserDto> {
    public UserBaseClient(UseCaseInvoker invoker) { super(invoker, "userBaseEnrichment", UserDto.class); }
}
```

两个关键设计决策：

1. **函数式取值语义**：与 YAML 串联模式（子结果覆盖父 payload）不同，Java 调用总会保存/恢复父 payload，结果经返回值返回——避免"调用个子用例顺手把主管道数据冲掉"这类隐式副作用；
2. **Supplier 延迟解析 registry**：若 `UseCaseInvoker` 直接持有 `UseCaseRegistry`，则「registry 装配 → 解析 ref step Bean → step 依赖 client → client 依赖 invoker → invoker 依赖 registry」形成 Bean 创建循环（demo 的 `GreetingStep` 实测触发）。`Supplier<UseCaseRegistry>` 首次调用时解析并缓存，切断循环；同一手法也用于 `SubUseCaseStepFactory`。

demo 端点：`GET /api/v1/users/{id}/greeting`（`greetUser` 用例 → `greetingStep` Bean 内经 `UserBaseClient` 调用子用例组装问候语）。

### 5.9 AuthHandler 体系

```java
public interface AuthHandler {
    String scheme();                                                  // YAML 中 auth.scheme
    void apply(RestClient.RequestHeadersSpec<?> request, Map<String, Object> options);
    default void validate(Map<String, Object> options) {}             // 装配期校验
}
```

| scheme | options | 说明 |
|--------|---------|------|
| `none` | — | 无认证（缺省等效） |
| `basic` | `username`, `password` | HTTP Basic |
| `bearer` | `token` 或 `tokenProvider` | 静态令牌 / `TokenProvider` Bean 动态取牌（支持轮换刷新） |
| `apiKey` | `header`, `value` | 请求头 API Key（query 形式直接写进 url） |
| `clientCredentials` | `tokenUrl`, `clientId`, `clientSecret`, `scope?` | OAuth2 CC：自动换 token、缓存、提前 60s 过期；按 (tokenUrl, clientId) 分键经 `ConcurrentHashMap.compute` 原子刷新（同 key 并发只取一次、不同 key 互不阻塞）；令牌端点客户端默认连接 3s / 读取 10s（可经构造器注入自定义 RestClient） |
| 自定义 | 任意 | 实现 `AuthHandler` 注册 Bean，`scheme()` 即类型名；同名覆盖内置 |

### 5.10 事件发布（eventPublisher）

把六边形样板「`eventPublisher.publish(new XxxCreatedEvent(...))` + 出站适配器 afterCommit 外发」（architecture §7.3 铁律）下沉为框架能力：

```yaml
- name: publishSnapshotCreated
  type: eventPublisher
  config:
    event: "T(com.example.myapp.domain.event.SnapshotCreatedEvent).of(#payload.snapshotId, #body.userId)"
    publisher: snapshotEventPublisher   # 可选：多发布器时指定 Bean 名；缺省取容器中唯一实现
```

| 配置项 | 必填 | 说明 |
|-------|-----|------|
| `event` | 是 | SpEL 表达式，求值结果为领域事件对象（框架不感知具体类型） |
| `publisher` | 否 | `EventPublisher` Bean 名；缺省取容器中唯一实现（多实现须有一个 `@Primary`）。**装配期 fail-fast 校验**（不实例化 Bean）：Bean 不存在 / 类型不匹配 / 无实现 / 多实现无 `@Primary` 均启动即报错 |

**事务时机由框架统一保障**（把架构规则固化进框架的核心价值）：步骤检测到活动事务时注册 `TransactionSynchronization.afterCommit`，**提交成功后才回调** `EventPublisher.publish`——回滚不发布、实现方无需（也不应）自行处理事务同步；无事务时立即发布。纯副作用步骤：不改变 payload / vars / biz。

`EventPublisher` 是框架提供的出端口 SPI（`framework.core`），业务侧实现真实外发（Kafka / 事务性发件箱 / webhook）。afterCommit 之后发布失败无法回滚已提交事务——实现方需自行保证可靠性（重试 / 发件箱）并建议幂等。

## 六、RouterFunction 绑定与异常映射

### 6.1 绑定

```java
@Bean
RouterFunction<ServerResponse> useCaseRouterFunction(UseCaseRegistry registry, UseCaseProperties props) {
    RouterFunctions.Builder builder = RouterFunctions.route();
    for (UseCase useCase : registry.all()) {
        if (useCase.isShared()) continue;   // shared 用例不绑定路由
        builder.route(
            RequestPredicates.method(HttpMethod.valueOf(useCase.getEndpoint().method()))
                .and(RequestPredicates.path(useCase.getEndpoint().path())),
            request -> {
                StepContext ctx = StepContext.of(request, objectMapper);
                Object payload = useCase.execute(ctx);
                return ServerResponse.status(useCase.getEndpoint().status())
                        .contentType(MediaType.APPLICATION_JSON)
                        .body(ApiResponse.success(payload));
            });
    }
    builder.onError(thrown -> true, (thrown, request) -> toErrorResponse(thrown));
    return builder.build();
}
```

所有 endpoint 用例汇入**一个** RouterFunction Bean；启动日志打印路由表（demo 实测输出）：

```
shared usecase [userBaseEnrichment] steps=[loadUser, toDto]
route: GET /api/v1/users/{id} -> usecase [getUser] steps=[start, validateInput, loadUserBase]
route: GET /api/v1/users/{id}/profile -> usecase [getUserProfile] steps=[start, loadUserBase, fetchCredit, checkCreditPass, logCredit, encodeUserId, userProfileTransformer, saveSnapshot]
route: GET /api/v1/users/token/{token} -> usecase [getUserByToken] steps=[start, decodeToken, loadUserBase]
route: GET /api/v1/users/{id}/greeting -> usecase [greetUser] steps=[start, GreetingStep]
route: POST /api/v1/user-snapshots -> usecase [createUserSnapshot] steps=[start, validateBody, checkUserExists, logCreation, toSnapshot, saveSnapshot]
```

函数式路由与注解式 `@RestController` 可共存（demo 的下游 stub 即为注解式）。

**入口职责（router 在管道执行前后做的事）**：
- 执行前往 biz 区种子化 `traceId`（优先取 `X-Request-Id` 请求头，经白名单 `[A-Za-z0-9_-]{8,128}` 校验——防日志注入/响应头分裂，不合法或缺省生成 UUID），同步写入 MDC（键 `traceId`，供 `%X{traceId}` 全链路关联）；成功/错误响应均回填 `ApiResponse.traceId`；
- StepContext 暂存于 request attributes，使 onError 异常处理器也能拿到 traceId；
- 管道结束后清理 MDC 中 `biz.*` 前缀键与 `traceId` 键，防止容器线程复用导致日志串号。

**请求体读取规则**：空体 → null；JSON 内容类型（缺省视为 JSON，含 `+json` 后缀）→ Jackson 严格解析，**语法错误抛 `StepValidationException` 映射 400**（明确报错而非静默置 null 导致误导性 schema 明细）；其他内容类型按纯文本返回 String。

### 6.2 异常映射矩阵（自包含于 router，无需 @RestControllerAdvice）

| 异常 | 状态码 | code | message |
|------|-------|------|---------|
| 领域/框架异常（`ErrorCoded` 或提供 `getErrorCode()`） | `error-mappings` 配置 → `@ResponseStatus` → **`ErrorCoded.defaultHttpStatus()`** → 500 | 异常的 errorCode | <500 透传业务消息；≥500 固定文案 |
| 校验失败（`StepValidationException`） | 默认 400（`defaultHttpStatus()`），可被配置覆盖 | 配置的 errorCode，缺省 `VALIDATION_ERROR` | schema 明细 / 模板消息 |
| `HttpStepException` / `RestClientResponseException` / `ResourceAccessException` | 502 | `DOWNSTREAM_ERROR` | 固定文案 |
| 兜底 | 500 | `INTERNAL_ERROR` | 固定文案，绝不回显内部消息 |

`StepExecutionException` 先沿 cause 链解包再匹配。响应信封沿用原 solution 的 `ApiResponse(code, data, message, timestamp, traceId)`。

## 七、扩展指南

1. **自定义 step（最常用）**：`@Component("riskCheck") class RiskCheckStep implements DataTransformer { … }` → YAML `ref: riskCheck`。复杂业务逻辑保持 Java 实现、可单测，配置只负责编排。
2. **自定义 step 类型**：实现 `StepFactory`（`type()` 返回如 `kafkaProducer`）注册 Bean → YAML `type: kafkaProducer`。框架自动并入装配器。
3. **自定义认证**：实现 `AuthHandler` 注册 Bean（如 `scheme() = "hmac"`）。
4. **自定义编解码算法**：实现 `Codec` 注册 Bean（如 SM4、企业私有编码），`algorithm()` 即 YAML 中的算法名。
5. **覆盖 HTTP 客户端**：定义名为 `useCaseRestClient` 的 Bean（自定义超时/代理/拦截器），框架默认连接 3s / 读取 10s。
6. **非 HTTP 驱动**（暂缓，2026-08-19 决策暂不考虑）：若未来需要消息消费者/CLI 驱动同一套管道，管道外入口已是 `StepContext.standalone()`（无入站请求）；届时如需富请求语义，为驱动侧提供 `ServerRequest` 适配或扩展 `StepContext` 的请求视图即可。

  - `GET /api/v1/users/u1`（带 `X-Request-Id: trace-caller-001`）→ 200 信封 + `"traceId":"trace-caller-001"`（调用方 traceId 透传）
  - `GET /api/v1/users/u1/profile` → 完整管道：starter 装载 biz → **子用例 userBaseEnrichment 加载用户** → 下游 stub 校验 Bearer 头返回信用分 → **validator 校验 `credit.score >= 600` 通过** → **logging step 输出「用户 u1 信用分: 760 (A)」** → **encoder 生成 `encodedId: "dTE="`** → 自定义 ref step 合并 → dataSaver 生成 `snapshotId`

  - `POST /api/v1/user-snapshots`（合法体）→ 200，isolate 子用例旁路确认用户存在，`ownerName` 参与快照组装

  - `POST /api/v1/user-snapshots`（userId 不存在）→ 404 + `USER_NOT_FOUND`（经 isolate 子用例抛出）
  - `GET /api/v1/users/u1/greeting` → 200，`greetingStep` Bean 内经 `UserBaseClient`（`AbstractUseCaseClient` 基类）调用子用例返回 `{"greeting":"Hello, Alice","invokedFrom":"java"}`；不存在用户 → 404（领域异常穿透 Java 调用边界）
  - 下游不可达 → 502 + `DOWNSTREAM_ERROR`

### 实测踩坑记录（本轮新增）

1. **Spring 7 `MapAccessor` 行为变更**：自 Framework 6.1 起，`MapAccessor.canRead` 仅当 key 存在于 Map 时才认领（为表达式编译服务），探测缺失 key（如 `#body.userId`，体中无该字段）会落到反射访问器抛 `EL1008E`；且自 Framework 7 起该类已 deprecated forRemoval。框架注册宽容的 `LenientMapAccessor`（Map 一律认领、缺失返回 null，注册为唯一 Map 访问器），恢复配置作者直觉语义——validator/starter 探测可选字段不再 500。
2. **Boot 对 `Map<String, Object>` 配置的列表绑定失真**：step config 为开放 Map 时，YAML 列表（`required: [userId, name]`）经属性扁平化后被绑定成索引 Map（`{0=userId, 1=name}`），导致 JSON Schema 的 `required` 静默失效。validator 工厂在装配期递归把「键全为非负整数」的 Map 还原为 List——自定义 step 的 config 若含嵌套列表需同样留意。
3. **networknt 3.x API 重写**：`JsonSchemaFactory` 系 API 已废弃，改为 `SchemaRegistry.withDefaultDialect(SpecificationVersion.DRAFT_2020_12).getSchema(node)` + `schema.validate(node)` 返回 `List<Error>`；3.0.x 基于 Jackson 3（`tools.jackson`），与 Boot 4 兼容。
